# Mighty Mouse v0.3.0

Mighty Mouse v0.3.0 introduces test-time compute scaling, canonical host provenance validation, structured activation telemetry, and the MCP v5 `agent_execute` interface.

## Release changes

- **Canonical Compute Scaling Policy & Pinning**:
  - Pinned compute-scaling policy contracts with bounded Best-of-N candidate generation (1 to 8 variations).
  - Configurable temperature schedules with dynamic annealing across variations.
  - Consensus strategies (`min_diff`, `unanimous`) with winner-only workspace mutation.
  - Bounded missing-file coverage recovery governed by `feedback_loop_enabled` policy flags.

- **Authoritative Provenance & Activation Invariant**:
  - Enforced fail-closed canonical host runtime context (`AdapterRuntimeContext`) through `HostAdapter.solve`.
  - Prohibited configuration-derived or spoofed task provenance from activating compute-scaling pins.
  - Single state-resolution path ensuring identical policy resolution for execution and telemetry.

- **Structured Activation Telemetry**:
  - Recorded canonical `compute_scaling` telemetry block in `last_agent_run.json`.
  - Controlled activation reasons (`exact_compatible_pin`, `no_exact_compatible_pin`, `missing_or_invalid_task_category`, `no_runtime_context`, `planner_stage`).
  - Observational-only logging with exact pin identity, expanded effective temperature schedules, and policy parameters.

- **MCP v5 & Canonical Agent Execution**:
  - Bumped `MCP_TOOL_CONTRACT_VERSION` from 4 to 5 (14 total tools).
  - Added `agent_execute` MCP tool routing directly to `HostAdapter.solve`.
  - Preserved `run` as adaptive routing and policy selection without code execution.
  - Required explicit re-onboarding via `setup_workspace(..., replace=True)` for v4 adapter identities.
  - Maintained clear separation: `agent_execute` performs execution only, without automatic verification, signal recording, or policy mutations.

## Upgrade & Compatibility Notes

- **Adapter Re-onboarding**: Workspaces configured with MCP tool contract v4 fail closed as stale and require running `setup_workspace(..., replace=True)`.
- **Scaling Pins**: Previously pinned scaling configurations under v4 execution profiles will not match v5 execution profiles and must be re-pinned under the new profile.
- **Legacy Invocations**: Unpinned executions and legacy `solve()` entrypoints continue to execute unscaled single-response passes with complete backwards compatibility.
